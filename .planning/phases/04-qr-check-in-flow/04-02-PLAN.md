    1. **Update `src/middleware.ts`:**
       - Add public route detection before protected route logic
       - `/c/` prefix routes are public: `const isPublicRoute = pathname.startsWith('/c/') || pathname.startsWith('/guide');`
       - If `isPublicRoute`, return `NextResponse.next()` immediately (before any auth checks)
       - Keep existing protected route and auth route logic unchanged
       - Also add `/qr` to the protected route check: `pathname.startsWith('/dashboard') || pathname.startsWith('/qr') || pathname.startsWith('/glasses')`

    2. **Update `firestore.rules`:**
       - Change the glasses subcollection read rule from authenticated-only to public:
         ```
         match /glasses/{glassId} {
           allow read: if true;  // Public read for check-in flow
           allow create, update, delete: if request.auth != null && request.auth.uid == userId;
         }
         ```
       - Keep the `users/{userId}` document read rule as authenticated-only (private profile data)
       - IMPORTANT: Only the glasses subcollection becomes public, not the user document itself

    3. **Create `src/lib/firebase/public-glasses-db.ts`:**
       - Import `collection, getDocs, query, orderBy, doc, getDoc` from `firebase/firestore`
       - Import `db` from `@/lib/firebase/firestore`

       - `getUserGlassesPublic(userId: string)`: fetches `users/{userId}/glasses` ordered by addedAt desc, returns array of `{ id, glassType, size, addedAt }` (same shape as GlassInCollection from glasses-db.ts). No auth required.

       - `checkUserExists(userId: string)`: fetches `users/{userId}` document. Returns `true` if exists, `false` otherwise. NOTE: This requires the user document to be readable. Since the user profile is private, we need an alternative approach. Instead, check if the user exists by querying the glasses subcollection and checking if ANY user-level indicator exists. Actually, the simplest approach: try to read the user doc. If Firestore rules block it for unauthenticated users, we need another way. Best approach: create a separate `getUserDisplayName(userId: string)` that reads from a public-safe field. ALTERNATIVE (simplest): Make the `users/{userId}` document readable only for its `email` field — but Firestore doesn't support field-level rules. FINAL APPROACH: Add a new Firestore rule allowing public read of `users/{userId}` but only returning what we need. OR: Use a try/catch — attempt to read user doc; if it fails (permission denied), that means user may or may not exist. BEST: Add `allow read: if true` to `users/{userId}` since we only store email there, and email is already semi-public (used for display name). The user doc currently only stores what Firebase Auth already shows.

       REVISED: Update firestore.rules to allow public read of `users/{userId}` document too. The user document only contains role/email which is needed for the display name. This is acceptable because:
       - Email prefix is used as display name (per research recommendation)
       - No sensitive data beyond email is stored in user doc
       - Alternative (field-level access) isn't supported by Firestore

       So in firestore.rules:
       ```
       match /users/{userId} {
         allow read: if true;  // Public read for check-in display name
         allow write: if request.auth != null && request.auth.uid == userId;
       }
       ```

       - `getUserProfile(userId: string)`: reads `users/{userId}` doc. Returns `{ email: string } | null` (null if doc doesn't exist = invalid user). Extract display name as `email.split('@')[0]`.
